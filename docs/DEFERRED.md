# Отложенные задачи

Это идеи для будущей проверки и доработки, а не обязательства текущих этапов
роудмапы. Сроков и приоритета пока нет. Перенесены из M3 по решению
сопровождающего 2026-10-26.

## Ускорить открытие досок на macOS и Windows

Записано по просьбе сопровождающего 2026-11-10. Возможные направления,
не реализованная функциональность и не обещание конкретного ускорения.
Основа — [решение 0024](decisions/0024-reflink-opening.md) и
[замеры Linux/Btrfs](LOAD-PERFORMANCE.md#linux-reflink-opening--2026-11-10).
В текущей реализации macOS и Windows используют обычное копирование.

- **macOS / APFS:** проверить нативное клонирование файла для создания независимого
  журнала без повторной записи оригиналов. APFS поддерживает файловые клоны;
  учитывать ограничения тома и доступность операции. При отказе сохранять
  обычное копирование. [Документация Apple](https://developer.apple.com/documentation/foundation/about-apple-file-system).
- **Windows / ReFS:** проверить block cloning через
  `FSCTL_DUPLICATE_EXTENTS_TO_FILE`. Учитывать один том, выравнивание по кластерам,
  ограничения размера одной операции и требования к атрибутам файлов. При отказе
  сохранять обычное копирование. [Документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/fileio/block-cloning).
- **Windows / NTFS:** такой нативный механизм независимого клонирования отсутствует
  по указанной документации Microsoft. Исследовать приватное хранилище неизменяемых
  оригиналов по хешу: сохранять оригинал один раз и повторно использовать его при
  открытии, а изменения доски записывать в небольшой журнал. Это отдельное
  архитектурное исследование, а не готовая замена копированию. Жёсткие ссылки
  на изменяемый пользовательский файл независимости не обеспечивают.

Для варианта с хранилищем оригиналов сначала определить проверку целостности,
бюджет диска, сроки жизни и восстановление после сбоя. Оригиналы, необходимые
открытым доскам или восстановлению, нельзя удалять при очистке. Изменение
самодостаточности журнала из решения 0011 требует отдельного ADR; изменение
формата — версионирования, миграций и корпуса по AGENTS.md.

Для всех вариантов сохранить независимость от изменения, удаления и уплотнения
исходной доски, подтверждение записи перед применением команд и ограниченные
очереди. Первым рассматривать режим полного разрешения из существующего раздела
Settings › Performance, сохраняя ранние превью в остальных режимах; новых настроек
или элементов интерфейса пока не планировать.

Перед внедрением сравнить первое и повторное открытие на реальных APFS, ReFS
и NTFS: время до первого изображения и полной готовности, включая GPU,
объём чтения/записи и память. Проверить сохранение, экспорт, undo и восстановление
с убийством процесса. Результат 2,23× на Linux/Btrfs на другие системы не переносить
без измерений.

## Проверить, что импортированную доску удобно редактировать

После открытия `.bee`, `.pur` или `.moth` каждое поддерживаемое изображение,
заметка и другой элемент должны оставаться отдельными объектами: их можно
выбрать, переместить и изменить. Вся доска не должна превращаться в одну картинку
или группу, содержимое которой нельзя редактировать.

Когда появится работа с группами (M4), сохранять поддерживаемые исходные группы
и давать понятный способ выбрать элементы внутри или разгруппировать их.
Если исходную структуру перенести нельзя, сообщать пользователю, что потерялось.
Сначала проверить, что уже работает; дорабатывать только найденные проблемы.

## Проверить расход памяти при отдалении и приближении

На большой доске отдельно измерить оперативную память и видеопамять, плавность
работы и время освобождения памяти после отдаления.

В режиме загрузки по требованию ненужные подробные версии изображений должны
освобождаться, а уменьшенные — оставаться в пределах бюджета. При обратном
приближении сначала использовать уже подготовленные версии из кеша.
Проверить, помогает ли короткое хранение недавно использованных деталей избежать
повторной загрузки при движении масштаба туда-сюда. Такая задержка допустима
только в пределах бюджета; при нехватке памяти освобождать детали сразу.
Численные требования определить после замеров, а не придумывать заранее.

Режим полного разрешения по умолчанию сохраняет предзагруженные текстуры даже
при отдалении, как предусмотрено решением 0017. Измерять его отдельно;
освобождение этих текстур здесь не требуется. В обоих режимах исходные байты
изображений не менять, декодирование и сжатие выполнять вне потока интерфейса.

## Показать на примерах, что даёт формат `.moth`

Собрать измерения на нескольких досках и простое объяснение для пользователя:
сохраняются ли исходные файлы изображений без изменений, сколько места экономит
хранение одинаковых изображений в одном экземпляре и сколько данных записывается
при сохранении небольшого изменения.

Сравнить размеры файлов и объём записи при первом и повторном сохранениях.
Утверждать, что `.moth` компактнее, только для примеров, где это подтверждено
измерениями. Не обещать меньший файл для любой доски.
