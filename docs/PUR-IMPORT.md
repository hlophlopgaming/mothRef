# PureRef (`.pur`) import specification

Date: 2026-10-18. Status: implemented MothRef behavior.
This document describes the current importer, rather than the full M2 feature target.
Validation results and measurements are recorded in the [validation report](M2-IMPORT-VALIDATION.md).

## 1. Purpose and output

The importer transfers supported `.pur` content into a new MothRef board.
The result consists of images and plain text notes that can then be edited
and saved as `.moth`.

The source `.pur` is opened read-only. The importer preserves embedded image
bytes without re-encoding, creates new UUIDv7 identifiers for items, and converts
their stacking order into MothRef fractional indices. Source identifiers are used
only to resolve references and sort items; item identity is not preserved across
two independent imports.

This implementation does not export back to `.pur`, edit the source file, or
synchronize subsequent changes with PureRef.

## 2. Supported format generations

### PureRef 2.x

The reader recognizes the known fixed `2.0`/`2.1` container header layouts.
The container holds a SQLite database whose parts are rearranged relative to a
normal SQLite file. The importer exposes a virtual database stream to the reader;
the entire database is neither copied into RAM nor written to a temporary SQLite file.

Table schemas are read from the SQLite catalog. Fields are matched by column name,
so different physical column orders observed in files produced by PureRef 2.1.2
and 2.1.3 are supported.

A restricted SQLite reader implemented in Rust is used, without C SQLite.
It supports the simple column declarations generated by Qt. Complex SQL declarations,
incompatible column sets, missing required tables, and UTF-16 databases are rejected.
This is not a general-purpose reader for arbitrary SQLite databases.
Other container header variants may also be rejected.

### PureRef 1.x

A separate reader handles the legacy binary format. It first locates PNG payloads
and records their offsets, then reads placements and resolves references to repeated
image instances. Each image's bytes are subsequently loaded and emitted separately.
The entire file is not retained in memory. PNG scanning uses windows of approximately
64 KiB and handles markers crossing window boundaries.

The positive legacy corpus contains version `1.10`. Selecting the 1.x reader does
not imply verified compatibility with every historical variant.

## 3. Invocation and import pipeline

1. The user opens a `.pur` through the file picker, passes it as a command-line
   argument, or drops it onto the window. Extension matching is case-insensitive.
2. The application uses an available empty board or attempts to create a new tab.
   This path does not insert into an occupied board. If a new tab cannot be created,
   the import is not applied to an occupied board.
3. An `ImportPur` request is sent to the background storage worker. File reading,
   hashing, and original-image writes run outside the UI thread.
4. The file size, header, and container MD5 checksum are validated.
   There is no option to open a file despite a checksum mismatch.
5. The reader extracts records, and `moth-import` converts supported items into
   MothRef rectangles, transforms, and content. Unsupported items count as skipped.
6. Original images are staged in the application's own recovery directory and
   synchronized to disk. Identical bytes are identified by BLAKE3 and share one
   staged original. During parsing, memory holds bounded metadata for pending
   insertions rather than all images.
7. After successful parsing, insertions are sorted by source `z`, with the source
   numeric `id` breaking ties. `Command::Insert` commands, new UUIDv7 identifiers,
   and fractional stacking indices are then created.
8. Each insertion uses the existing journal-before-acknowledgment path: required
   originals and commands become durable before the UI receives acknowledgment.
   A final checkpoint is written, and the import becomes one undo/redo step.
9. The UI receives commands, references to staged originals, and the skipped-item
   count. Skipped items trigger a partial-import warning. The resulting board is
   saved as `.moth`; the source `.pur` path does not become its save destination.

The importer transfers item geometry. PureRef camera settings, scroll position,
background, and last viewing state are not restored.

## 4. Images and transforms

### Supported for 2.x

- Nonempty embedded image payloads with positive dimensions from the database.
  Missing or invalid dimensions cause the item to be skipped.
- Multiple placements of one original as separate scene items.
- Translation, uniform scaling, frame rotation, and reflection representable by
  MothRef's current transform model.
- Rectangular cropping, content translation within the frame, uniform content
  scaling, and axis reflection. Scale is adjusted for the MothRef renderer's
  aspect-preserving cover behavior.
- Composition of parent transforms into child transforms. The group hierarchy
  is flattened into individual items.

The crop contour must contain five points: a start point and four line segments
closing a rectangle in the expected order. Curves, arbitrary polygons, and other
contour encodings may be skipped.

The resulting frame matrix must be finite and affine, with nonzero uniform scale
and perpendicular axes, within numerical tolerances. Perspective, shear, and
nonuniform scaling are unsupported. The inner image matrix permits translation,
reflection, and uniform axis-aligned scaling; separate rotation or shear of the
content within its frame is not transferred.

Inherited opacity is composed through the parent chain. If the item's final
opacity differs from `1`, the entire item is skipped. Alpha already present in
the image bytes remains in the original.
Missing `flags`, `0`, and a value with only the least significant bit set are
accepted; other bits cause a skip. PureRef flag semantics are not fully implemented.

### A narrower subset is supported for 1.x

Embedded PNGs and their repeated placements are imported when their translation,
uniform scale, rotation, and reflection matrices are supported. PNG bytes are
preserved exactly as stored in `.pur`; any external original from which PureRef
may have created the PNG is not recovered.

Only a full-image rectangle consisting of five points is accepted: the frame
size must match the PNG, `matrix_before_crop` must be the identity matrix,
`scale_crop` must equal `1`, and `x_crop`/`y_crop` must equal negative half-width
and half-height. Other legacy crop variants are skipped.
An image containing text children is also skipped entirely; its child notes are
not extracted separately.

### Byte preservation and decoding are separate stages

The importer neither decodes pixels nor re-encodes images. For 2.x it uses database
dimensions; for 1.x it uses PNG header fields. The container MD5 is checked, but
individual image payloads are not separately checked against `images.checksum`.

Whether the preserved bytes can be displayed depends on subsequent decoding in
`moth-io`. Successful import alone does not establish that every payload is a valid
image or uses a supported codec. Decode failures are handled by the application's
separate placeholder/error mechanism.
PureRef animation playback parameters are not transferred. Image filters and
settings, such as grayscale and sampling mode, are not restored as PureRef properties.

## 5. Notes, groups, and metadata

Plain note text up to 32 KiB in UTF-8 is imported. MothRef calculates the frame
size; original typography, colors, and note styling are not reproduced.
Supported frame transforms are preserved.

For 2.x, a note is skipped if `fixed_size` is present, its final opacity differs
from `1`, or its text contains `<`. The last check is a conservative filter,
not a complete HTML parser: a plain text note containing `<` is also skipped.
For 1.x, `opacity == 65535` and the absence of text children are additionally
required. Child note trees are not flattened into independent notes.

Drawings, group styling and containers, hierarchy, locks, comments, item names,
source paths/URLs, and most other PureRef metadata are not transferred to the
MothRef scene. Supported children of 2.x groups retain their composed coordinates,
rather than the parent object itself. `sort_order` is not used in place of the
`z` and `id` ordering described above.

Referenced external files and URLs are neither opened nor downloaded. Placements
without an available embedded payload are skipped. There is no automatic relinking.

## 6. Limits and memory use

All limits apply simultaneously:

- Total `.pur` size: **up to 4 GiB inclusive**, or 4,294,967,296 bytes.
  Larger sources are rejected before payloads are read.
- One SQLite record: **up to 32 MiB**, including image bytes and all other fields
  in that record. An image of exactly 32 MiB may exceed the record limit because
  of record overhead.
- One legacy PNG original: **up to 32 MiB**.
- Reader-accounted metadata: **8 MiB**, with an additional **8192** limit on
  records/items in the relevant structures. Groups and unsupported items may
  also consume this budget.
- Storage worker pending insertions: **8192 placements** and **8 MiB** under its
  separate metadata accounting. Repeated placements count separately regardless
  of byte deduplication.
- 2.x parent chain: **up to 64 levels**; invalid references and cycles are rejected.
- 1.x text nesting: **up to 32 levels**. The parsing depth limit does not imply
  support for importing child notes.
- One note's text: **up to 32 KiB of UTF-8**, or 32,768 bytes.

4 GiB is a file-size limit, not permission to allocate that much RAM. Streaming
still requires buffers: memory may hold the complete current SQLite record or PNG,
temporary parsing buffers, and bounded metadata. The 8 MiB checks are accounting
budgets, not a promise that total RSS will be exactly 8 MiB.
Decoding, CPU/GPU caches, and disk space for originals and journals have separate
application limits.

A file smaller than 4 GiB can therefore still be rejected because of an oversized
record, item count, metadata, an unsupported schema, or an I/O error.

## 7. Skips, errors, and recovery

There are three distinct outcomes:

1. **Complete import of supported content:** the reader finishes without error,
   and the converter reports no skipped items.
2. **Partial import:** the reader finishes, but some items cannot be represented.
   Supported items are added, and the UI displays a warning.
3. **Operation error:** size, structure, or checksum validation fails; a budget is
   exceeded; references are invalid; or reading, staging, or journal writing fails.
   The error is propagated to the caller; successful completion is not acknowledged.

`Summary.images`, `Summary.text`, and `Summary.unsupported` describe item conversion
results. The skip count is not a complete inventory of lost fields: for example,
names and comments may be discarded from an imported image without increasing
`unsupported`. A result of `0 skipped` does not establish full equivalence to the
PureRef board.

Before commands are applied, a parsing error leaves the scene unchanged; already
created staging files may remain in the recovery directory. Import is not one
atomic disk transaction: commands are journaled individually. If storage fails or
the process exits during command application, the journal may contain only part
of the imported items. Recovery uses the durable journal prefix; there is no
automatic rollback of the entire operation.

A single undo/redo step is formed after successful import completion. Undo history
lives in session memory; this mechanism does not promise to preserve it across
restarts. Expected reader errors are returned through `Result`; an outer
`catch_unwind` contains unexpected panics in normal builds. This does not guarantee
recovery after OOM, an OS crash, or hardware failure.

## 8. Verified compatibility

The repository contains small captured files for legacy version 1.10 and container
version 2.1 from PureRef 2.1.3. The local `FemaleFighterPosesPack.pur` from PureRef
2.1.2 was also checked: 198.54 MiB, 175 images, 0 skipped items. Validation through
the real storage worker covered `.moth` save/load, the identities of all 175 original
blobs, and grouped undo/redo. In the recorded run, durable import took 0.929 seconds,
and peak validation-process RSS was 18.64 MiB.

These measurements cover headless import and storage validation. They do not
measure the full application with image decoding and GPU use. A physical 4 GiB file,
all historical PureRef versions, and every content variant have not been tested.
The 4 GiB boundary is covered by a virtual source-length test.

To reproduce validation of the local file:

```sh
cargo xtask pur FemaleFighterPosesPack.pur
```

This command is stricter than the normal UI: any skipped item fails qualification.
It uses an isolated temporary recovery directory, saves a temporary `.moth`, checks
loading and undo/redo, then removes its own temporary files. The source `.pur`
remains in place. The private artwork file is not included in the public corpus.
